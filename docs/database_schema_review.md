# Database Schema Review

Review and finalization of the PostgreSQL database schema for the Nexus PM stack. This document details index optimization, foreign key constraints, security rules, normalization boundaries, and vector database indexing.

## 2. Table-by-Table Schema Review

### 2.1 Accounts App
#### `accounts_user`
- **Primary Key**: UUID.
- **Constraints**:
  - `email`: `UniqueConstraint` (case-sensitive check is recommended at application level or via PostgreSQL CITEXT extension).
  - `username`: `UniqueConstraint`.
- **Indexes**: Default unique indexes generated by Django on `email` and `username`.
- **Review**: Using UUIDs instead of sequential integers provides strong security against ID enumeration attacks.

### 2.2 Organizations App
#### `organizations_organization`
- **Primary Key**: UUID.
- **Constraints**:
  - `slug`: `UniqueConstraint` (used for routing: `/org/{slug}`).
- **Indexes**: Unique index on `slug`.

#### `organizations_membership`
- **Primary Key**: UUID.
- **Constraints**:
  - `unique_together = ('user', 'organization')`: Prevents duplicate memberships.
- **Indexes**:
  - Unique composite index on `(user_id, organization_id)`.
  - Individual foreign key index on `organization_id` (Django default) and `user_id` (Django default) to optimize membership lists.

### 2.3 Projects App
#### `projects_project`
- **Primary Key**: UUID.
- **Indexes**:
  - `projects_project_org_status_idx` composite index on `('organization_id', 'status')`.
  - `projects_project_updated_at_idx` index on `('-updated_at')`.
- **Optimization**: The composite index on `(organization_id, status)` optimizes the primary workspace route, which loads projects within a specific organization filtered by active/archived status.

#### `projects_task`
- **Primary Key**: UUID.
- **Indexes**:
  - `projects_task_project_status_idx` composite index on `('project_id', 'status')`.
  - `projects_task_assignee_status_idx` composite index on `('assignee_id', 'status')`.
- **Optimization**:
  - The `(project_id, status)` index speeds up Kanban board rendering where tasks in a project are grouped/queried by status.
  - The `(assignee_id, status)` index optimizes user dashboard lists ("My Tasks").

### 2.4 Notifications App
#### `notifications_notification`
- **Primary Key**: UUID.
- **Indexes**:
  - `notifications_user_read_idx` composite index on `('user_id', 'read')`.
- **Optimization**: High-throughput read/write. The composite index on `(user_id, read)` is critical for the persistent topbar notification counter, which frequently checks `WHERE user_id = ? AND read = False`.

### 2.5 Audit App
#### `audit_auditlog`
- **Primary Key**: UUID.
- **Indexes**:
  - `audit_actor_created_idx` composite index on `('actor_id', '-created_at')`.
  - `audit_resource_idx` composite index on `('resource_type', 'resource_id')`.
- **Optimization**: Audit logs are append-only. The composite indexes support security audit audits (filtering user actions sorted by recency) and resource-specific logs (showing changes to a particular project or organization).

### 2.6 AI Vector Database (pgvector)
#### `ai_memory_entries`
- **Primary Key**: UUID.
- **Indexes**:
  - `ix_memory_agent_session` composite index on `(agent_id, session_id, user_id)`.
  - HNSW index on `embedding` using Cosine Distance (`vector_cosine_ops`).
- **Optimization**: Slicing memories by session and agent must be fast before running cosine similarities. The composite index ensures metadata filtering takes place before vector math.

#### `ai_documents`
- **Primary Key**: UUID.
- **Indexes**:
  - `ix_documents_org_project` composite index on `(org_id, project_id)`.

#### `ai_document_chunks`
- **Primary Key**: UUID.
- **Indexes**:
  - `ix_document_chunk_order` unique composite index on `(document_id, chunk_index)`.
  - HNSW index on `embedding` using Cosine Distance (`vector_cosine_ops`).

## 3. Normalization vs. Targeted Denormalization

### 3.1 Normalization (Standard Rules)
The transactional schemas (users, projects, memberships, tasks) are fully normalized to **Third Normal Form (3NF)**.
- Advantages: Zero redundant data, strict update integrity, and clear object isolation.

### 3.2 Targeted Denormalization Candidates (Read-Heavy Tuning)
For an enterprise system, certain read-heavy views are prone to $N+1$ query issues or expensive table joins:

1. **Project Member Counts**:
   - *Current*: Calculated dynamically via Django aggregations on `Membership`.
   - *Denormalization Alternative*: Store `member_count` on `projects_project`. Update this integer column via Django post-save/post-delete signals on `Membership`. This accelerates project card lists.
2. **Last Project Activity**:
   - *Current*: Evaluated by querying the latest `updated_at` timestamps on `projects_task`.
   - *Denormalization Alternative*: Store `last_activity_at` directly on `projects_project`, updated whenever a task is modified or created.

## 4. Scaling Considerations (pgvector & Partitioning)

### 4.1 HNSW vs. IVFFlat for Vector Indexes
- **IVFFlat (Inverted File Flat)**:
  - Pros: Faster build times, uses less memory.
  - Cons: Requires retraining when data shifts, lower recall accuracy.
- **HNSW (Hierarchical Navigable Small World)**:
  - Pros: High recall accuracy, updates dynamically when new document chunks are inserted.
  - Cons: High memory usage, slow build times.
- **Decision**: We choose **HNSW** for both `ai_memory_entries` and `ai_document_chunks`. Recommendations and RAG memory require high recall accuracy, and because documents are updated dynamically by users, rebuilding IVFFlat indexes would create maintenance bottlenecks.

### 4.2 Partitioning the Audit Log
The `audit_auditlog` table is write-heavy and will grow linearly.
- **Recommendation**: Implement **PostgreSQL Table Partitioning** by range on `created_at` (e.g. monthly partitions). This keeps active index trees small and makes it easy to archive/drop logs older than a retention window (e.g. 1 year) by dropping a partition rather than executing expensive `DELETE` queries.
